# safe-coding

## 概览

这个 skill 不是语法检查、格式检查或泛泛的代码审查工具。它用于约束 Codex 在修改业务代码前，先完成影响分析、风险判断和回归测试计划，尤其关注权限、租户、隔离、数据范围、公共方法调用链和核心业务流程。

使用本 skill 时，所有面向用户的分析、计划、风险说明、测试计划和测试证据都必须使用中文。

## 核心原则

- 改代码前先做影响分析，未经用户明确同意进入实现阶段，不修改代码。
- 先识别直接影响和间接影响，再讨论实现方案。
- 高风险代码必须先回答四个门禁问题。
- 测试不能只写“通过”，必须记录输入、期望结果、实际返回和失败日志。
- 优先寻找只改当前模块的办法，避免把局部需求扩散成跨模块重构。

## 适用场景

当用户提出以下任务时，应使用本 skill：

- 修改接口、服务、DAO、entity、schema、公共方法或共享工具方法。
- 改动权限校验、租户隔离、数据范围、组织/角色/成员关系、财务或会员相关逻辑。
- 新增导出、分页、查询过滤、状态流转、统计报表、异步任务、消息消费者或定时任务。
- 修改会被旧模块复用的类、函数、依赖注入对象或事件处理逻辑。
- 用户明确要求“改代码前先分析”“影响分析”“回归测试计划”“留测试证据”“高风险变更先确认”。

不要因为普通语法检查、拼写修正、格式化或纯样式建议触发本 skill。

## 阶段一：只分析和计划

在这个阶段只能读取代码、搜索调用链、分析影响和制定计划。除非用户明确批准进入实现阶段，不得编辑、创建、删除、格式化或重命名任何项目文件。

必须输出以下内容：

### 1. 改动范围

- 要改的文件：列出预计会直接修改的文件。
- 会调用或改动的公共方法：列出函数、类方法、接口、路由、任务入口、消费者入口等。
- 依赖这些方法的旧模块：列出已发现的调用方、复用方、旧接口、旧页面、旧任务或旧报表。

### 2. 影响分析

直接影响：

- 当前要改的类、接口、函数、路由、schema、DAO、service 或页面组件。
- 当前需求涉及的输入、输出、异常、分页、导出、状态流转或落账逻辑。

间接影响：

- 定时任务、后台任务、消息消费者、事件监听器。
- 报表、财务统计、会员列表、导出任务、缓存刷新、审计日志。
- 共享公共方法、权限中间件、租户过滤器、数据范围构造器。
- 可能依赖旧返回结构、旧状态枚举或旧查询条件的模块。

### 3. 安全与边界检查

必须检查并说明：

- 权限：是否会绕过角色、菜单、操作权限或对象级权限。
- 租户：是否会跨 tenant、workspace、org、company 或门店读取/修改数据。
- 隔离：是否影响用户、组织、部门、成员、财务账户等隔离边界。
- 数据范围：是否正确限制本人、所属组织、下级组织、授权范围或分页/导出范围。
- 敏感数据：是否会扩大手机号、邮箱、身份证、财务数据、账单、余额、token、密钥等暴露范围。

### 4. 回归测试计划

必须写清要跑哪些回归测试，并说明每个测试要验证什么。至少包含：

- 新功能测试。
- 直接关联旧功能回归。
- 核心业务流程全链路测试。

如果项目里已经有对应测试命令、脚本、接口用例或手工验证入口，应列出具体命令或路径；如果没有，应说明需要补充的最小验证方式。

## 高风险改动门禁

当 Codex 判断想要改动以下高风险代码时，必须先停在分析阶段，并回答四个问题：

- 为什么要改？
- 现在有哪些地方调用了？
- 有没有只改当前模块的办法？
- 改完需要回归哪些功能？

高风险代码包括但不限于：

- 权限、认证、授权、租户隔离、数据范围、审计、财务、会员核心资料。
- 公共 service、公共 DAO、基础 schema、共享工具方法、全局中间件。
- 定时任务、消息消费者、事件监听器、状态机、最终落账或对账逻辑。
- 被多个模块调用的查询、导出、分页、统计和状态变更方法。

如果没有完成这四个问题，不得直接修改高风险代码。

## 阶段二：用户批准后再实现

只有在用户明确表示可以改代码、开始实现、按计划修改或类似意思后，才进入实现阶段。

实现时应遵循：

- 只改已分析范围内的文件；如发现必须新增范围，先补充影响分析。
- 优先只改当前模块，避免改公共方法签名；确实要改时同步更新所有调用方。
- 保持权限、租户、隔离和数据范围条件不弱化。
- 对导出、分页、异常提示、状态流转、落账等用户可见行为保持兼容，除非需求明确要求改变。
- 对复杂或高风险逻辑添加必要但简短的注释。

## 阶段三：测试至少拆三步并留证据

测试结果不能只写“测试通过”。每一步都要记录：输入是什么、期望结果、实际返回、失败时留下的日志或错误信息。

### 第一步：新功能测试

验证本次新增或修改的功能是否正确，例如：

- 导出数据是否完整且受权限/数据范围限制。
- 分页参数、排序、筛选条件是否生效。
- 异常提示、空数据、非法参数和边界值是否符合预期。

记录格式：

- 输入：接口参数、页面操作、任务参数或测试数据。
- 期望结果：应返回的数据、状态码、文件内容、提示文案或数据库变化。
- 实际返回：真实响应、页面结果、日志摘要或测试输出。
- 失败日志：失败时保留命令输出、请求 ID、异常堆栈或关键日志位置。

### 第二步：直接关联旧功能回归

验证和本次改动直接相邻的旧功能没有坏，例如：

- 会员列表。
- 财务统计。
- 权限过滤。
- 旧导出入口。
- 旧查询接口。
- 旧状态变更入口。

必须说明旧功能为什么和本次改动有关。

### 第三步：核心业务流程全链路测试

验证核心流程没有被局部改动破坏。默认链路可以按项目实际业务调整，但必须覆盖类似：

登录授权 -> 创建/查询 -> 状态流转 -> 最终落账

如果项目不是财务或订单类业务，应替换为该项目最核心的端到端流程，并说明替换原因。

## 中文输出要求

无论项目语言、框架或参考资料是什么，只要使用本 skill：

- 对用户说中文。
- 影响分析写中文。
- 修改计划写中文。
- 回归测试计划写中文。
- 测试证据写中文。
- 专业术语可以保留英文缩写，例如 API、DAO、DTO、JWT、RBAC、SQL、tenant。
